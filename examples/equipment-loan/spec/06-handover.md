# 开发交接说明

> 虚构示例。给立项后接手正式开发的团队。原型代码在 `../app/`，需求和模型在本目录。

## 1. 先读哪些文件

| 文件 | 内容 |
|---|---|
| `01-rules.md`、`01-decision-tables.md` | 13 条业务规则、2 张决策表，以及阶段 5b 中用户确认的 5 条澄清 |
| `02-stories.md` | 11 个功能故事、6 个非功能故事、61 条验收标准 |
| `golden-cases.md` | 5 个必须跑通的真实场景 |
| `models/` | 用例图、活动图、序列图、状态机图、类图，每张图附说明卡 |
| `trace.csv` | 每条验收标准、规则、决策表行、状态转换对应的代码和测试 |
| `changes/archive/` | 两次规格变更（001 取消原因和通知、002 重复通知和逾期费权限）的原因和改动 |

## 2. 数据模型

来自类图 `models/07-class-domain.puml`。

| 表 | 对应的类 | 说明 |
|---|---|---|
| `people` | Person / Borrower / StaffMember | 泛化用单表加 `kind` 字段；借用人和员工的专有字段按类型校验 |
| `equipment` | Equipment | 单价以分为单位；"贵重"= 单价 > 5000 元，读取时计算，不存储 |
| `loans` | Loan | 状态取值与状态机一致；借用日期、应还日期、归还日期存 `YYYY-MM-DD` 文本，避免时区错一天 |
| `loan_items` | Loan–Equipment | 一张借用单至少 1 件设备 |
| `approvals` | Approval | 每张单每个审批角色最多一条；不同意必须有原因（数据库约束） |
| `agreements`、`late_fees` | Agreement、LateFee | 每张单最多一条 |
| `audit_entries` | AuditEntry | 只能新增，数据库触发器禁止修改和删除 |
| `notifications` | Notification | 原型中只做系统内消息 |
| `settings` | — | 逾期费单价、上限、提醒工作日数，以及演示控制项 |

借用单也有触发器禁止删除（C-02）。

## 3. 关键设计决策及原因

| 决策 | 原因 |
|---|---|
| 状态只能通过 `src/domain/loan/transition.ts` 中的一个函数修改；转换表 `transitions.ts` 与状态机图一一对应 | 守卫、通知和操作记录不会被绕过；测试会读取状态机图并与转换表比对，两边不一致时测试失败 |
| 决策表写成数据（`src/rules/decision-tables.ts`），代码查表，不写成 if/else | 规则改动时只改表；测试检查每张表完整且没有重叠 |
| 权限集中在 `src/auth/permissions.ts`，服务端拒绝越权；界面用同一份配置隐藏按钮 | 界面隐藏只是方便，真正的检查在服务端 |
| 只有"已批准、借出中、已逾期"的借用单占用设备；"已申请"不占用，批准时再检查一次库存 | 用户确认"先批准先得"（E18） |
| 等待名单先到先得：设备空出时，只让最早提交、且所需设备都已空出的那张回到"已申请" | 用户在 5b 确认 |
| 逾期费在归还时由柜台当场收取，系统登记为已缴；没有减免操作 | BR-10、X2：以后统一收取，不再特批 |
| 过了应还日期、但到期检查还没运行就来归还的，系统先标为已逾期，再按逾期办理 | 用户在 5b 确认，避免因检查时间差而少收费 |
| 审批提醒只发给当前轮到的审批人 | 用户在 5b 确认；部门负责人只审设备管理员已同意的单 |
| 资产标签在数据库事务之外逐件核对，全部通过后再进入事务 | 外部系统调用不应占用数据库事务；任何一件不通过，整张单不借出（BR-11） |

## 4. 原型中模拟的部分及正式开发的替代方案

| 原型中 | 正式开发 |
|---|---|
| 资产登记系统：`src/adapters/asset-registry/mock.ts`，由设置项控制"不可用"和"无效标签" | 按 `index.ts` 中的接口对接学院资产登记系统；只读，不回写 |
| 通知：写入 `notifications` 表，页面上显示 | 接入邮件或企业微信；发送失败时的重试和记录 |
| 每日到期检查：设备管理员页面上的按钮，`runDailyChecks()` | 每天定时运行同一个函数；去掉"模拟今天"设置项，日期取服务器时间（东八区） |
| 登录：演示账号、本地密码、连续 5 次失败锁定 15 分钟 | 建议接入学校统一身份认证（需要学校信息中心确认）；会话密钥必须通过 `SESSION_SECRET` 设置，生产环境缺少时程序拒绝启动 |
| 数据库：SQLite 单文件 | 按学院运维要求选择数据库；表结构和迁移在 `drizzle/` |

## 5. 原型没有验证的要求

| 要求 | 说明 |
|---|---|
| NFUS4 AC3：高峰期每天 60 单、3 人同时操作 | 原型只验证了约 4800 张借用单下列表和保存的速度（远低于 2 秒和 1 秒），没有做并发压力测试 |
| NFUS6 AC3：借用记录 3 年后归档和销毁 | 需要和学院档案规定一起设计 |

标为"原型演示"的要求（NFUS2 AC3、NFUS3 AC2、NFUS5 AC1、AC2）已在角色走查中演示，截图在 `reviews/5c/`。

## 6. 明确不在原型范围内

- E20 部门负责人不在时代理审批（用户决定正式开发时再做）
- E21 人员离职或毕业时的未还设备
- E32 归还时设备损坏的登记和赔偿
- 账号管理（原型中账号由演示数据预置）
- 节假日日历（"工作日"只排除周末）

## 7. 已知限制

- 台账中 3 条没有借用日期的记录（JY-0904、JY-0907、JY-0908）按用户决定没有导入，保留在原台账备查；导入报告见 `app/data/import-report.md`（运行 `npm run setup` 后生成）。
- 并发：同一张借用单被两人同时操作时，后提交的一方会收到"刚被其他人处理过，请刷新"；没有更细的锁。
- 查找使用模糊匹配，数据量大幅增加后需要建全文索引。
- 统计在内存中计算，适合原型数据量；正式系统建议按月预先汇总。

## 8. 测试

| 命令 | 内容 | 数量 |
|---|---|---|
| `npm test` | 决策表每一行、状态机每条转换（成功、守卫失败、越权、终止状态）、每条验收标准、演示数据与规格一致、代码结构检查 | 150 |
| `npm run test:e2e` | 5 个黄金案例、演示脚本排练、"填错后改正再提交"，从界面操作 | 6 + 1 + 1 |

测试的有效性做过反向检查：故意在代码中埋入 18 个典型错误，测试全部发现（`reviews/5b-summary.md`）；界面测试也用埋错的方式确认能发现问题。
