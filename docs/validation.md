# 验证报告

**中文** | [English](validation.en.md)

PM/BA Panda 是怎么被验证和改进的：先和"不用 skill、直接让 Claude 做"对比，再用 skill 把一个完整项目从需求做到验收，把途中暴露的每个问题都改回 skill 里。

日期：2026-10-25 至 2026-10-26。示例项目：[`examples/equipment-loan/`](../examples/equipment-loan/)（虚构的学院设备借用系统）。

---

## 1. 和直接生成的对比

### 方法

- **Skill 组**：Claude 加载 skill，完成示例项目的阶段 0–4（需求、用户故事、UML、构建计划）。
- **对照组**：另一个 Claude 实例，不加载 skill，拿到同样的开场请求和同样三份材料（台账、申请单、借用规定），不能提问，要求写明假设。
- 评分标准共 8 项，在看结果之前定好。

### 结果

| 评分项 | 结果 | 说明 |
|---|---|---|
| UML 质量与跨图一致性 | **Skill 明显更好** | 对照组的活动图有至少 5 个动作放错泳道，序列图中有一条生命线在类图里不存在、消息对应不到类的操作、直接写"状态=…"绕过状态转换。按映射规则，这些会变成错误的权限和数据结构 |
| 条件组合完整性 | **Skill 更好** | Skill 组用决策表检查了所有条件组合；对照组用文字描述，引入第三个条件后组合没有列全 |
| 例外覆盖 | Skill 更系统 | Skill 组逐项过了例外清单；对照组散见约 17 项，但有 3 项是 skill 清单里没有的 |
| 隐藏规则 | Skill 略好 | 6/6 对 5/6，其中部分得益于可以向用户提问 |
| 推断与事实区分 | 持平 | 一个用出处标签，一个用假设列表 |
| 边界情况 | 持平 | 对照组还考虑了跨月、跨年和闰年 |
| 验收标准 | 各有所长 | Skill 组每条都能追溯到规则编号；对照组大量用台账中的真实数据做例子，更具体 |
| **材料矛盾的发现** | **对照组更好** | 对照组把台账每一行都拿规定核对了一遍，发现的"实际执行与规定不一致"比 skill 组多（其中也有一处误判）。Skill 组当时只做结构性提取，没有逐行核对 |

### 对比暴露的 skill 问题

最重要的发现：skill 组在缺少逐行核对的情况下，**把两个黄金案例改写成了符合规定的样子，而不是把材料和规定的矛盾交给用户**；应还日期的算法也和台账口径不一致。这说明"像 BA 一样挖需求"不能只靠原则，必须有具体做法。

### 据此做的改进

| 改进 | 位置 |
|---|---|
| 材料考古增加**逐行核对**：每条记录都用已知规则检查，不符合的分为隐藏规则、执行与规定不一致、漏办或拖延 | `references/artifact-mining.md` 第 3 节 |
| 矛盾清单增加"执行与规定不一致"类型，必须由用户裁决 | 同上 |
| 黄金案例引用材料中的人、记录、日期、金额时必须与材料一致；对不上时列为矛盾，不能改写任何一方 | `SKILL.md` 阶段 1c；一致性检查 H7 |
| 验收标准优先用材料中的真实（脱敏）数据做例子 | `references/acceptance-criteria-guide.md` |
| 例外清单补充 3 项（批准后长期不领取、归还时设备损坏、自己审批自己），共 33 项 | `references/exception-checklist.md` |
| 提问库和非功能清单补充数据迁移 | `references/elicitation-questions.md`、`references/nfr-catalogue.md` |
| 阶段 6 增加演示脚本 | `SKILL.md` 阶段 6、`references/plain-language-cards.md` |

改进后重做示例的材料考古：9 条台账记录逐行核对，新增 1 处矛盾，黄金案例和应还日期口径全部与台账一致。

## 2. 完整跑通一个项目

用改进后的 skill 把示例项目继续做完阶段 5（搭建）和阶段 6（验证与交付），直到验收。途中每发现一个属于 skill 本身的问题，就记录下来，最后统一与用户确认后改进 skill。共记录 23 个。

### 发现的问题和改进

**检查脚本和清单的漏洞（8 个）**：规格或模型里的错误，检查没有发现，到写代码时才暴露。

| 问题 | 改进 |
|---|---|
| 状态机上同一个通知画了两次（转换上一次，进入状态时又一次），照图实现会重复通知 | 一致性检查新增 A13，自动阻断。用修正前的模型复测，A13 能直接拦住 |
| 状态机上的"到期前提醒""关闭逾期提醒"在任何规则里都找不到依据 | 新增 H8：每个动作都要在图上注明依据，脚本自动检查。在示例上找出 7 处，全部补上依据或请用户确认 |
| 状态机漏画了效果（归还后要释放设备、取消后要通知借用人） | 新增 H9：用规则和验收标准反向核对效果 |
| 类图里没有地方存"取消原因"和"通知" | G4 扩展：效果需要保存的数据，类图里都要有地方存 |
| 权限表和一条验收标准互相矛盾 | C3 扩展为用例图、权限表、验收标准三方一致 |
| 构建计划的转换表和状态机图对不上 | 开工前就绪检查增加逐行核对 |
| 一致性检查每次重跑都覆盖人工检查结果 | 脚本只更新自动部分，人工结果保留 |
| 追溯检查认不出用循环生成的测试名，报出假缺口 | 追溯脚本可以读取测试运行报告，失败的测试不算覆盖 |

**流程衔接（3 个）**：台账里有 3 条记录缺日期、无法导入新系统，阶段 1 的逐行核对记下了"没有日期"，却没有从"能否导入"的角度提出来；构建计划里的账号数和规格对不上。改进：逐行核对增加"能否导入新系统"一列，导不进的记录在阶段 1 就请用户决定；就绪检查核对计划中的数字。

**默认技术栈和环境（6 个）**：只有日期的字段存成时间戳会因时区错一天；React 19 在表单提交失败后会清空用户已填的内容；网络受限时字体和组件库下载失败；测试工具版本与预装浏览器不匹配；框架默认选项增加不必要的复杂度。改进：`references/default-stack.md` 补充对应约定，新增"网络受限或离线时"一节。

**测试和验证方法（6 个）**：

| 问题 | 改进 |
|---|---|
| 测试第一轮全部通过，但故意埋入 18 个典型错误时漏掉 2 个 | 新增反向检查工具 `scripts/mutation_check.py`，阶段 5b 起必须做 |
| 静态检查本身也会错：一开始把"退出登录时删除 cookie"当成删数据，改窄后又漏掉了真正的删除 | 每条静态检查都要埋一次违规，确认它会报错 |
| 有 3 个问题只在界面上出现，单元测试发现不了：错误信息不显示、批准后看不到确认、表单内容被清空 | 角色走查每一步都要断言页面上出现了确认或错误信息，必须包含"填错 → 改正 → 再提交" |
| 演示脚本里随手选的一件设备正被一张逾期单占用，现场演示会失败 | 演示脚本必须按原文自动排练 |
| 界面测试按内部字段名找元素，埋入的错误让测试因"找不到元素"失败，看起来抓到了，其实什么都没验证 | 界面测试按页面上看得到的文字和标签找元素 |
| 种子数据第一次运行就有 2 处错误（审批顺序颠倒、缺少一种状态） | 种子数据校验测试，并用故意改坏的数据确认它有效 |

这些方法汇总在 [`references/verification-playbook.md`](../references/verification-playbook.md)。

### 改进之后又抓到的问题

改进后用新的脚本把示例重新检查了一遍：

- 反向检查发现，修好的"表单内容被清空"没有任何自动测试保护，以后被改回去也不会有人知道。已补上界面测试，并确认它能抓住这个错误。
- 新的出处检查找出了 7 个没有注明依据的动作，其中 1 个确实从来没人说过，交给用户确认。

## 3. 最终结果

| 检查 | 结果 |
|---|---|
| 单元和集成测试 | 150 项全部通过 |
| 从界面操作的端到端测试 | 8 项全部通过（5 个黄金案例、演示脚本排练、"填错后改正再提交"） |
| 反向检查 | 埋入 21 个典型错误（规则、权限、计算、通知、静态检查、界面），测试全部发现 |
| 追溯检查（读取测试运行报告） | 61 条验收标准、每行决策表、11 条状态转换、5 个黄金案例都有通过的测试，缺口 0 |
| 一致性检查 | 0 阻断；剩余 4 条警告已在人工检查中逐条确认 |
| 角色走查 | 4 个角色主流程和例外流程全部走通；无障碍扫描（WCAG 2 A/AA）没有发现问题 |
| 发布前脱敏 | 全部文件中没有个人信息、本地路径或真实密钥；演示手机号使用不可能属于任何人的 10 开头号段 |

## 4. 局限

- **只验证了一个领域**：设备借用（物品借还 + 审批流）。其他类型的业务还没有完整跑过。
- **对比只各运行一次**，不能排除偶然性。
- **"用户"由 Claude 扮演**：示例中用户的回答和 skill 组出自同一个 Claude，存在自我迎合的风险。对比测试已经暴露过一次（改写黄金案例），之后的逐行核对和 H7 检查就是为此加的，但风险没有完全消除。
- **反向检查的错误清单是人写的**：它证明测试能发现这 21 类错误，不证明能发现所有错误。

## 5. 下一步

- 换一个领域（例如会议室预约或报销审批），两组各运行 3 次。
- 由第三个 Claude 实例按一份事先写好的"真实情况"扮演用户，避免自问自答。
- 积累业务模式库（审批流、工单处理、预约排期、物品借还、案件管理），让阶段 1 的提问更有针对性。
