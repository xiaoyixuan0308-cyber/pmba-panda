# UML → 代码映射规则

本文件是这个 skill 的核心：它规定每一种模型元素在原型里变成什么。

- **阶段 3 建模时**读"总表"，知道每个元素会落到哪里，避免画出无法实现或含义模糊的图。
- **阶段 4 做构建计划时**逐节对照，把模型元素逐个转成实现清单，并填入追溯矩阵。
- **阶段 5 构建时**按各节的"实现要点"和"必写测试"执行。

代码示例使用默认技术栈（Next.js + Drizzle + SQLite，TypeScript）。换栈时，映射关系不变，只换写法。

## 2. 类图 → 数据库与领域模型

### 2.1 类

- 每个持久化的类对应一张表，表名为术语表中英文名的复数小写（`Loan` → `loans`）。
- 每张表有自增主键 `id`。如果业务上有编号（借用单号、病历号），另设唯一的业务编号字段，界面显示业务编号而不是 `id`。
- 每张表加 `createdAt`、`updatedAt`。需要审计的表不在本表存修改历史，统一写审计日志（见 7.5）。

### 2.2 属性类型

| UML 类型 | 数据库字段 | 说明 |
|---|---|---|
| String | text | 有长度上限的在服务端校验 |
| Integer | integer | |
| Decimal / 金额 | integer（以分为单位） | 不用浮点数存金额 |
| Boolean | integer（boolean 模式） | |
| Date / DateTime | integer（timestamp 模式） | 统一存 UTC，界面按本地时区显示 |
| 枚举 | text + 允许值校验 | 允许值必须与术语表一致 |
| 派生属性（`/` 开头） | 不存储，读取时计算 | 例：`/isOverdue` |

可见性：`-` 私有属性不出现在接口返回和页面上（例如密码哈希）；`+` 公开属性可以展示。

### 2.3 操作

- 类图里的操作变成服务层函数，命名沿用操作名（`approve()` → `approveLoan()`）。
- 不是每个操作都对外暴露。只有用例图里有对应用例的操作，才有页面或操作入口；其余是内部函数。
- 会改变状态的操作，内部必须调用状态变更函数（见 3.2），不能直接改状态字段。

### 2.4 多重性

| 关联两端 | 实现 |
|---|---|
| 1 对 1 | 一侧放唯一且非空的外键 |
| 1 对 0..1 | 可选一侧放唯一、可空的外键 |
| 1 对 * | "多"的一侧放非空外键 |
| 0..1 对 * | "多"的一侧放可空外键 |
| * 对 * | 关联表，两个外键组成联合唯一 |
| 下限 ≥ 1（如 1..*） | 外键表达不了，在创建时的服务函数里校验，并写测试 |
| 上限有具体数字（如 0..3） | 在服务函数里校验数量，并写测试 |

### 2.5 组合与聚合

- **组合（实心菱形）**：部分不能脱离整体存在。外键非空，删除整体时级联删除部分；整体和必需的部分在同一个事务里创建。
- **聚合（空心菱形）**：部分可以独立存在。外键可空，删除整体时把外键置空，或在仍有关联时禁止删除（选哪种要在构建计划里写明）。
- 检查菱形画在哪一端：菱形在**整体**一端。画反了，级联方向就反了。

### 2.6 泛化

两种实现方式，在构建计划里写明选哪种及原因：

- **单表 + 类型字段**（默认）：子类特有属性不多时使用。父类表加 `type` 字段，子类属性设为可空，并按类型在服务端校验必填项。
- **子类表**：子类特有属性多，或子类各自有不同关联时使用。父类一张表，每个子类一张表，子类表的主键同时是指向父类的外键。

参与者的泛化（例如"兽医是一种员工"）不在这里处理，见 6.1。

### 2.7 关联类

关联类变成带额外字段的关联表，例如"学生–课程"的关联类"选课记录"带 `grade` 字段。

### 必写测试

- 每个下限 ≥ 1 或有数字上限的多重性：一个违反时被拒绝的测试
- 每个组合关系：删除整体后部分也被删除
- 每个聚合关系：删除整体后部分仍在（或按约定被禁止删除）

## 3. 状态机图 → 状态字段与状态转换

### 3.1 状态

- 状态机所描述的实体上加一个 `status` 字段，允许值就是状态机里的状态名（来自术语表）。
- 默认值是初始伪状态指向的那个状态。
- 终止状态没有出去的转换，进入后实体只读（除非规格另有规定）。
- 复合状态只存最底层的子状态，父状态在需要时由子状态推出。

### 3.2 转换：唯一入口

所有状态转换写成一张常量表，状态只能通过一个函数改变：

```ts
// src/domain/loan/transitions.ts
export const loanTransitions = [
  { id: "T1", from: "Requested", event: "approve", to: "Approved",
    roles: ["Manager"], guard: "hasStock",      rule: "BR-03" },
  { id: "T2", from: "Requested", event: "reject",  to: "Rejected",
    roles: ["Manager"], guard: null,            rule: "BR-04" },
  { id: "T3", from: "Approved",  event: "checkOut", to: "OnLoan",
    roles: ["Clerk"],   guard: "agreementSigned", rule: "BR-05" },
  // ...
] as const;

// src/domain/loan/transition.ts
export async function transitionLoan(loanId, event, actor) {
  // 1. 查出当前状态
  // 2. 在表中找 from = 当前状态 且 event 匹配的转换；找不到 → 拒绝
  // 3. 检查 actor 的角色是否在 roles 中；不在 → 拒绝
  // 4. 执行 guard；不通过 → 拒绝，并返回违反的 BR 编号
  // 5. 在同一事务中：执行 exit 动作 → 更新 status → 执行转换效果 → 执行 entry 动作 → 写审计日志
}
```

规则：

- **任何地方都不能直接写 `status` 字段**，只能调用状态变更函数。
- 转换的触发（event）就是界面上的操作按钮或定时任务；界面只显示当前状态下该角色可用的操作。
- 守卫（guard）写成独立的判断函数，函数名或注释带上 BR 编号。守卫必须在服务端执行，界面上的禁用按钮只是辅助。
- 效果（effect，图上 `/` 后面的部分）在同一事务里执行，例如生成通知、记录日期。

### 3.3 entry / exit / do

| 图上写法 | 实现 |
|---|---|
| `entry / 动作` | 进入该状态时在同一事务内执行 |
| `exit / 动作` | 离开该状态时在同一事务内执行 |
| `do / 活动` | 持续性的活动，用定时任务或后台检查实现（原型里可以用"打开页面时检查"简化，需在构建计划里说明） |

写转换表时，把每条转换的效果和相关 BR、AC 交叉核对一遍，不要只照图抄：

- 图上的效果可能不全。规则说"有设备归还后通知等待的人"，归还转换就需要"释放设备"；AC 说"取消后借用人收到通知"，取消转换就要通知。图上漏了的，在代码里补上并在转换表旁注明依据，同时记入发现清单，阶段结束时问用户是否回改模型。
- 图上的效果可能重复。转换效果和目标状态的 entry 动作做同一件事时，只实现一次（一致性检查 A13）。
- 动作找不到依据（何时做、对谁做都没人说过）的，先按最朴素的理解实现，标为待确认，在阶段评审中问用户（检查项 H8）。

### 3.4 时间触发

`after(14 days)` 或 `when(到期日已过)` 这类触发，用定时检查实现：一个按日期筛选实体并调用状态变更函数的任务。原型里提供一个"运行到期检查"的管理员按钮，方便演示，同时在 README 中说明生产环境应改为定时任务。

### 必写测试

- 转换表中的每一条转换：一个成功的测试
- 每个守卫：一个守卫不通过时被拒绝的测试
- 至少挑选每个状态下一个不允许的操作：被拒绝的测试
- 终止状态：任何操作都被拒绝
- 每次成功转换：审计日志多了一条

## 4. 活动图 → 流程逻辑与守卫

### 4.1 动作与泳道

- 每个动作对应一个服务函数调用，或界面上的一个步骤（填表、确认、上传）。
- 泳道决定谁能执行这个动作：执行前在服务端检查角色，与 CRUD 矩阵一致。
- 系统泳道里的动作是自动执行的，不需要用户操作。

### 4.2 决策点

- 每个决策点变成一个分支判断，出边上的守卫条件必须互斥且覆盖所有情况（加 `[else]` 兜底）。
- 守卫引用业务规则编号；条件组合复杂时引用决策表，代码里调用决策表对应的函数（见 7.1）。
- 如果某个决策的结果会改变实体状态，它必须对应状态机里的一条转换。活动图和状态机说法不一致时，以术语表和业务规则为准，先修模型再写代码。

### 4.3 fork / join（并行）

并行分支在原型里不需要真正的多线程，它表达的是"这几件事互不依赖、都要完成"。实现方式：

- fork 时为每个并行分支创建一条子任务记录（例如三条检查记录，状态均为"待完成"）。
- 每个分支由各自的角色独立完成，顺序不限。
- join 变成一个闸门函数：所有子任务都完成后才允许进入下一步。界面上显示每个分支的完成进度。

```ts
// join 闸门
export function allChecksComplete(checks) {
  return checks.length === 3 && checks.every(c => c.result !== "Pending");
}
```

注意：如果某个分支可能提前结束整个流程（例如一项检查不通过就直接拒绝），在活动图里要画清楚。不要让一个分支离开 fork/join 区域后，join 还在等它，否则流程会卡死。

### 4.4 循环与回流

活动图里的回流（例如"治疗后重新评估"）通常对应状态机里回到之前状态的转换。实现时走状态变更函数，并保留每一轮的记录（追加新记录，不覆盖旧记录）。

### 4.5 结束节点

- 活动终点（实心圆外加圆圈）：整个流程结束，通常对应状态机的终止状态或一个稳定状态。
- 流程终点（圆圈加叉）：只结束这一个分支，其他分支继续。

### 必写测试

- 每个决策点的每个出边：一个测试
- 每个 join 闸门：差一个分支未完成时被拒绝，全部完成后通过
- 每条回流：能走回去，且旧记录保留

## 5. 序列图 → 服务层调用

### 5.1 生命线

| 生命线 | 实现 |
|---|---|
| 参与者（小人） | 页面上的用户操作 |
| 界面或控制对象 | 页面 / Server Action |
| 领域实体（来自类图） | 服务函数 + 数据访问 |
| 外部系统 | 适配器接口，原型中用模拟实现 |

生命线名称必须是类图中的类名或术语表中的名称。

### 5.2 消息

- 同步消息 → 函数调用；返回消息 → 返回值。
- 消息的先后顺序就是服务函数内部的执行顺序。
- 自调用消息 → 内部校验或私有辅助函数（例如 `validateApplication()`）。
- 创建消息 → 插入新记录。
- 涉及多个实体写入的一段消息，在同一个事务中完成；在构建计划里写明事务边界。

### 5.3 组合片段

| 片段 | 实现 |
|---|---|
| alt | if / else，每个分支的条件与活动图的守卫一致 |
| opt | 带条件的执行 |
| loop | 循环；有次数上限的写明上限 |
| par | 与活动图的 fork/join 一致，按 4.3 实现 |

### 5.4 外部系统

- 每个外部系统定义一个接口（例如 `RegistryLookup`），原型里写一个模拟实现，返回固定或随机的演示结果。
- 界面上凡是用到模拟结果的地方，标注"模拟数据"。
- 超时和不可用的情况也要模拟，对应的错误提示来自 NFUS。

### 必写测试

- 每张序列图的主路径：一个集成测试，断言调用后数据库的最终状态
- alt 的每个分支：一个测试
- 外部系统不可用：一个测试，断言系统给出了明确的错误提示而不是崩溃

## 6. 用例图 → 角色、功能与权限

### 6.1 参与者

- 每个人类参与者 → 一个角色（存在用户表的 `role` 字段，或用户–角色关联表）。
- 参与者泛化 → 子角色继承父角色的全部权限，再加上自己的权限。实现时在权限配置里展开，不在代码里写继承判断。
- 外部系统参与者 → 不是角色，按 5.4 做成适配器。

### 6.2 用例

- 每个用例 → 一个操作入口（页面或按钮）+ 一个服务函数。
- 用例与参与者之间的连线 → 该角色有权使用这个入口；与 CRUD 矩阵、角色视角表三方必须一致。
- 用例名称使用"动词 + 名词"，与服务函数名对应（"审批借用申请" → `approveLoan`）。

### 6.3 include 与 extend

- **include**：被包含的用例每次都会执行 → 一个共用函数，被所有包含它的用例调用。例：多个用例都包含"记录审计日志"。
- **extend**：扩展用例只在特定条件下发生 → 主用例中一个带条件的分支，条件写在扩展点上，并对应一条业务规则。例："登记逾期罚款"在"归还设备"时，满足"已逾期"条件才执行。
- 箭头方向检查：include 从基础用例指向被包含用例；extend 从扩展用例指向基础用例。

### 必写测试

- 每个角色：能访问自己的入口，访问别的角色的入口被服务端拒绝（不仅是界面隐藏）
- 每个 extend：条件满足和不满足各一个测试

## 7. 非 UML 产出 → 代码与测试

### 7.1 决策表

- 一张决策表变成一个纯函数：输入是条件，输出是结果。
- 优先把决策表直接写成数据，函数按表查找，这样表和代码不会对不上。
- 测试采用表格驱动：决策表的每一行都是一个测试用例。

```ts
// BR-02：审批级别（决策表 DT-01）
const approvalLevelTable = [
  { amountOver5000: false, external: false, levels: ["Manager"] },
  { amountOver5000: false, external: true,  levels: ["Manager", "Finance"] },
  { amountOver5000: true,  external: false, levels: ["Manager", "Director"] },
  { amountOver5000: true,  external: true,  levels: ["Manager", "Finance", "Director"] },
];
```

### 7.2 CRUD 矩阵

- 矩阵转成一份权限配置（角色 × 实体 × 操作）。
- 每个服务函数执行前查这份配置；界面根据同一份配置决定显示哪些按钮。
- 矩阵中标"仅本人"的权限（例如申请人只能看自己的申请），在查询时加过滤条件，并写测试。

### 7.3 角色视角表

- 每个角色有自己的首页，内容就是视角表中"登录后首先看到什么"。
- 导航菜单按角色显示，内容来自"能做什么"一栏。

### 7.4 验收标准与黄金案例

- 每条 AC 至少一个测试，测试名带上故事和 AC 编号。
- 每个黄金案例一个端到端测试，按案例中的步骤操作，断言期望结果。
- 端到端测试像真人一样找页面元素：按页面上看得到的文字、按钮名和标签找（例如 Playwright 的 `getByRole("button", { name: "确认归还" })`、`getByLabel("已当场收取")`），不按内部字段名或 CSS 选择器找。按字段名找时，"界面上的复选框没有传到服务端"这类错误会让测试因"找不到元素"而失败，看起来测试抓到了问题，实际上什么都没验证。
- 每个端到端测试用一份全新的演示数据，互不影响。

### 7.5 非功能用户故事

| 类别 | 实现 |
|---|---|
| 安全 | 登录、会话、服务端权限校验 |
| 审计 | 统一的审计日志表：谁、什么时间、对哪条记录、做了什么、前后值 |
| 数据保留 | 归档标记字段，查询默认排除已归档记录 |
| 性能 | 在测试里对关键查询设时间上限，数字来自 NFUS |
| 无障碍 | 表单有标签、可键盘操作、颜色对比度达标；用自动检查工具扫描主要页面 |

## 8. 命名与追溯约定

- 代码中的实体名、状态名、角色名、字段名一律取自术语表的英文名，不允许出现术语表里没有的同义词。
- 实现业务规则的位置加注释：`// BR-07`。
- 状态转换在转换表里带编号：`T1`、`T2`……对应状态机图上的转换标签。
- 测试名带编号：`FUS3-AC2: 未签协议不能借出`、`DT-01 R4`、`GC-02: 外部供应商大额申请`。每个测试名里逐条写出编号，不要用循环加变量拼出测试名（如 `` `DT-02 ${rule}` ``）：读源码做追溯时认不出这种名字。确实要用循环时，阶段 6 运行 `build_trace.py` 加 `--test-report`，从测试运行报告读取真实的测试名。
- `trace.csv` 的列：故事编号、AC 编号、BR 编号、模型元素（图名 + 元素名或转换编号）、代码位置、测试名。

## 9. 常见映射错误

| 错误 | 后果 | 预防 |
|---|---|---|
| 在多个地方直接修改状态字段 | 绕过守卫，出现非法状态 | 只允许状态变更函数写 `status` |
| 守卫只在界面上做（禁用按钮） | 绕过界面即可违规操作 | 守卫必须在服务端执行 |
| 组合关系没加级联删除 | 留下没有归属的孤儿记录 | 按 2.5 实现并测试 |
| 组合菱形画反 | 级联方向反了，删除错误的数据 | 菱形画在整体一端 |
| 图里、代码里状态名写法不同 | 追溯断裂，界面显示不一致 | 统一取自术语表 |
| 1..* 的下限没校验 | 出现"没有明细的订单"之类的数据 | 创建函数中校验并测试 |
| 权限只在界面隐藏 | 直接调用接口就能越权 | 服务端按 CRUD 矩阵校验 |
| fork 后某分支提前结束，join 仍在等它 | 流程卡死 | 按 4.3 画清楚提前结束的路径 |
| 决策表改了，代码里的 if-else 没改 | 规则不一致 | 决策表写成数据，代码按表查找 |
| 外部系统直接写死在代码里 | 无法演示失败情况，难以替换 | 按 5.4 做适配器和模拟实现 |
