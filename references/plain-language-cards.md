# 说明卡与评审摘要

这个 skill 的用户不懂技术。本文件规定两类面向人的文字怎么写：

- **说明卡**：每张 UML 图配一张，给用户看懂这张图、检查这张图。
- **评审摘要**：每个阶段关卡一页，给不会翻规格文件的业务方或领导看。

1. 写作规则

## 1. 写作规则

1. **用用户的业务词。** 图里的英文名在说明卡里换成术语表中的中文名（或用户自己的叫法），第一次出现时在括号里附英文名，方便对照图："借用单（Loan）"。
2. **不出现技术词。** 不写"实体""外键""枚举""守卫""事务"。必须提到时，换成业务说法："守卫"说成"前提条件"，"状态转换"说成"状态从……变成……"。
3. **用用户自己的案例举例。** 讲解时优先拿黄金案例走一遍，而不是讲抽象规则："按你上周说的那张借笔记本的单子，它在这张图里是这样走的……"
4. **只说用户需要判断的事。** 不解释 UML 语法本身的历史和细节，只解释读懂这张图必需的符号。
5. **检查问题要具体。** 不问"这张图对吗？"，而是问"拒绝之后，借用人还能重新提交同一张单吗？图里画的是不能。"
6. **一张卡不超过一屏。** 内容多就拆，或者只讲最关键的部分，其余留在规格文件中。
7. **推断出来的内容单独标出。** 图里来自推断或模式库的部分，在说明卡中明确说"这部分是我推出来的，请特别确认"。

## 2. 说明卡模板

每张图一张，保存为 `spec/models/<图文件名>.card.md`，与图片放在一起。

```markdown
# <图的中文标题>

![](<图文件名>.png)

## 这张图讲什么
<一两句话：这张图回答的业务问题。>

## 怎么读
<只列这张图里实际用到的符号，每个一句话。从第 3 节的读图指南中选取。>

## 用你的案例走一遍
<选一个黄金案例，用 3–6 句话说明它在图上怎么走。>

## 它决定了 app 的哪部分
<一两句话，例如"这张图决定了借用单在系统里有哪几种状态、每种状态下能点哪些按钮"。>

## 请你检查
1. <具体问题，指向图中的某个位置>
2. ...
（3–5 个问题，推断出来的部分放在最前面）

## 我做的假设
<没有就写"无"。有的话逐条列出，并标明对应的待确认编号。>
```

## 3. 五种图的读图指南与检查问题

### 3.1 用例图

**这张图讲什么**：谁会用这个系统，每个人能用它做哪些事。

**怎么读**

| 符号 | 意思 |
|---|---|
| 小人 | 一类使用者（一个岗位，不是某个具体的人） |
| 带"system"标记的小人 | 和这个系统打交道的另一个系统 |
| 大方框 | 这个系统的范围，框里的是系统要做的事 |
| 椭圆 | 一件使用者想用系统完成的事 |
| 小人到椭圆的实线 | 这类人可以做这件事 |
| 空心三角箭头（小人之间） | 箭头起点的人能做终点的人能做的所有事，还能做更多 |
| 虚线箭头 + include | 做前一件事时，一定会顺带做后一件事 |
| 虚线箭头 + extend | 只有在方括号里的条件满足时，才会多做这件事 |

**决定 app 的哪部分**：每个角色登录后能看到哪些菜单和按钮。

**检查问题示例**
- 有没有哪个岗位漏掉了？有没有画了但实际上不用系统的岗位？
- <某角色> 能做的事里，有没有哪件其实不该让他做？
- 带条件的那几件事（extend），条件写得对吗？

### 3.2 活动图

**这张图讲什么**：一件事从头到尾怎么走，每一步由谁做。

**怎么读**

| 符号 | 意思 |
|---|---|
| 竖条（泳道）和顶部的名字 | 这一列里的步骤都由这个岗位来做 |
| 实心黑点 | 流程开始 |
| 圆角方框 | 一个步骤 |
| 菱形 + 方括号里的条件 | 在这里要做判断，按条件走不同的路 |
| 粗横线（分叉） | 下面几件事可以同时进行，互不等待 |
| 粗横线（汇合） | 上面几件事都做完了，才能继续 |
| 往回的箭头 | 不满足条件时回到前面重做 |
| 带圈的黑点 | 整个流程结束 |
| 带叉的圆圈 | 这条路到此为止 |

**决定 app 的哪部分**：每一步谁来操作、按什么顺序、在哪里需要判断、哪些事情可以同时进行。

**检查问题示例**
- 用你说的 <案例> 走一遍，每一步都在图上吗？顺序对吗？
- <某步骤> 放在 <某岗位> 那一列，实际上是他做的吗？
- 在 <某判断> 那里，除了图上画的几种情况，还有别的情况吗？
- 同时进行的那几件事，真的互不依赖吗？有没有哪件要等另一件的结果？

### 3.3 序列图

**这张图讲什么**：完成一件事时，系统内部各部分按什么顺序配合。这张图偏技术，用户重点看顺序和分支是否符合业务即可。

**怎么读**

| 符号 | 意思 |
|---|---|
| 顶部的方框和小人 | 参与这件事的人或系统部分 |
| 往下的虚线 | 时间从上往下走 |
| 实线箭头 | 一方请另一方做某件事 |
| 虚线箭头 | 做完之后的回复 |
| 指向自己的箭头 | 自己内部检查一下 |
| alt 框 | 按条件分成几种情况，每种情况走框里的一格 |
| opt 框 | 只在条件满足时才做 |
| loop 框 | 重复做，直到条件不满足 |

**决定 app 的哪部分**：系统在后台处理这件事的先后顺序，以及出问题时怎么回应。

**检查问题示例**
- 系统在 <某一步> 之前先检查 <某条件>，这个顺序对吗？
- 检查不通过时，提示用户的那句话合适吗？
- <外部系统> 连不上时，图里画的处理方式可以接受吗？

### 3.4 状态机图

**这张图讲什么**：一张单子（或一件物品）在系统里会经历哪些状态，什么事情会让它从一个状态变成另一个状态。

**怎么读**

| 符号 | 意思 |
|---|---|
| 实心黑点 | 刚创建时 |
| 圆角方框 | 一种状态 |
| 方框里的 entry / exit / do | 进入这个状态时、离开时、停留期间系统会自动做的事 |
| 箭头 | 状态的变化 |
| 箭头上的文字 | `编号 什么操作 [前提条件] / 变化时顺带做的事` |
| 带圈的黑点 | 这张单子的生命结束，之后不再变化 |

**决定 app 的哪部分**：单子上显示的状态有哪些，每种状态下能点哪些按钮，以及系统什么时候会自动改变状态。

**检查问题示例**
- 有没有漏掉的状态？比如"暂停""等补材料"？
- 到了 <某状态> 之后，还能回到之前的状态吗？图里画的是 <能/不能>。
- 从 <状态A> 到 <状态B> 的前提条件是 <条件>，对吗？
- 哪些状态是"结束了"？结束之后真的不会再有任何变化吗？

### 3.5 类图

**这张图讲什么**：系统需要记住哪些东西，每样东西有哪些信息，它们之间是什么关系。

**怎么读**

| 符号 | 意思 |
|---|---|
| 方框 | 系统要记住的一类东西，例如借用单、设备 |
| 方框中间一栏 | 这类东西要记录的信息 |
| 方框下面一栏 | 可以对它做的操作 |
| 两个方框之间的线 | 它们之间有关系 |
| 线两端的数字 | 数量关系，例如 `1` 和 `0..*` 表示"一个借用人可以有零张或多张借用单" |
| 实心菱形 | 菱形那一端是整体，另一端是它的组成部分；整体删除了，部分也跟着删除 |
| 空心菱形 | 菱形那一端包含另一端，但另一端可以单独存在 |
| 空心三角箭头 | 箭头起点是箭头终点的一种，例如"借用人是一种人员" |

**决定 app 的哪部分**：系统里要填写和保存哪些信息，以及这些信息之间怎么关联。

**检查问题示例**
- <某东西> 要记录的信息里，有没有漏掉你们现在表格里有的列？
- 一张借用单可以同时借多台设备吗？图里画的是 <可以/不可以>。
- <整体> 删除后，<部分> 也一起删除，对吗？
- 有没有你们常说、但图里没有的东西？

## 4. 说明卡示例

以 `plantuml-pitfalls.md` 中的借用单状态机为例：

```markdown
# 借用单的状态变化

![](03-state-loan.png)

## 这张图讲什么
一张借用单从提交到结束，会经历哪几种状态，以及每次变化是什么引起的。

## 怎么读
- 圆角方框是状态，箭头是状态的变化。
- 箭头上的文字依次是：编号、什么操作、[前提条件]、变化时顺带做的事。
- 方框里的 entry / do / exit 是进入、停留、离开这个状态时系统自动做的事。
- 带圈的黑点表示这张单子结束了。

## 用你的案例走一遍
按你讲的"小王借投影仪"那一单（GC-01）：小王提交后是"已申请"（Requested）；
管理员确认有库存后批准，变成"已批准"（Approved），系统通知小王；
小王签了借用协议，办事员登记借出，变成"借出中"（OnLoan）；
到期没还，系统自动把它变成"已逾期"（Overdue）并提醒管理员；
小王归还时系统收取逾期费，变成"已归还"（Returned），这张单子结束。

## 它决定了 app 的哪部分
借用单上会显示这 6 种状态；每种状态下只出现能用的按钮
（例如"已批准"时才有"登记借出"）；到期检查会自动把逾期的单子标出来。

## 请你检查
1. 【推断】"已拒绝"之后单子就结束了，借用人如果想再借，需要重新提交一张新单。这样对吗？
2. "已批准"之后，借用人还能撤回吗？图里目前不能。
3. "已逾期"的单子归还时一定收费吗？有没有可以免收的情况？
4. 还有没有别的状态，比如设备坏了正在维修、借用人申请延期？

## 我做的假设
- 拒绝后不能重新打开原单（待确认 Q-07）。
```

## 5. 评审摘要模板

每个阶段关卡一份，保存为 `spec/reviews/<阶段号>-summary.md`。读者是业务负责人或领导，他们不看规格文件，也不一定看图。

规则：

- 一页以内，五分钟能读完。
- 不出现文件名、编号体系（BR、FUS、T3）、代码和技术词；必要时只说"第 3 条规则"。
- 先说结论，再说需要对方做什么。
- 待确认问题写成对方可以直接回答的句子，并写明需要谁回答。

```markdown
# <项目名>：<阶段名>评审

<日期> · <整理人>

## 这一阶段确定了什么
<3–5 条要点，业务语言。>

## 关键图
<可选。附一张最有代表性的图，配一句话说明。>

## 和现在的做法相比
<可选，阶段 1 及之后。说明解决了哪些痛点。>

## 需要您确认的问题
1. <问题>（建议请 <岗位> 回答）
2. ...

## 下一步
<一两句话：确认之后要做什么，大概需要什么。>
```

## 6. 评审摘要示例

```markdown
# 设备借用系统：需求挖掘评审

2026-10-25 · 产品 <姓名>

## 这一阶段确定了什么
- 系统涉及 4 类人：借用人、办事员、设备管理员，以及部门负责人（负责审批贵重设备并查看统计）。
- 借用分两种审批：一般设备由管理员批准；笔记本等贵重设备超过 5000 元，还要部门负责人批准。
- 整理出 9 条借用规则，其中借期规则因人而异：学生 14 天、教师教学用 30 天、贵重设备减半。
- 确认了 6 种特殊情况的处理方式，包括逾期、撤回申请、设备不足时排队。

## 和现在的做法相比
- 现在要在两张表格里重复登记设备编号，系统中只需登记一次。
- 现在逾期全靠管理员每周翻表格发现，系统会在到期当天自动提醒。

## 需要您确认的问题
1. 教师借设备用于非教学用途时，按学生的借期算吗？（建议请设备管理员回答）
2. 借用人离职或毕业时，没还的设备由谁负责追回？（建议请部门负责人回答）
3. 逾期费用的标准是多少？现行表格里没有统一金额。（建议请财务回答）

## 下一步
以上问题确认后，开始把规则写成具体的验收标准，预计再需要一次 30 分钟的确认。
```

## 7. 演示脚本

阶段 6 写入 `spec/06-demo-script.md`，供用户向领导或业务方演示原型。原则：

- 按"现在的痛点 → 系统怎么解决"组织，每一段对应 `01-as-is.md` 中的一个痛点。
- 每一段用一个黄金案例或材料中的真实记录来演示，观众能认出是哪件事。
- 每段写清楚：用哪个演示账号、点哪里、观众应该看到什么、要说的一两句话。
- 总长控制在 10 分钟左右；最后一段说明原型中模拟的部分和立项后需要业务部门配合的事项。

```markdown
# 演示脚本（约 10 分钟）

演示前：运行 `npm run setup` 恢复演示数据。

## 1. 逾期不再拖很久才发现（痛点 P4，约 2 分钟）
- 账号：manager@demo.local
- 操作：设置页把"模拟今天的日期"改为黄金案例中应还日期的次日 → 首页点"运行到期检查"
- 观众看到：该借用单变为"已逾期"，借用人和管理员都收到提醒
- 要说的话：现在逾期要等周五翻台账，系统在到期第二天就能发现。

## 2. ……

## 最后：原型和正式系统的区别（约 1 分钟）
- 资产登记系统、通知是模拟的；到期检查在正式系统中每天自动运行。
- 立项后需要业务部门确认的事项：……
```
