# 用户故事与验收标准写法

阶段 2 使用。用户故事说明"谁要什么、为什么"，验收标准（AC）说明"做到什么程度算完成"。AC 会直接变成测试（见 `uml-to-code-mapping.md` 7.4），所以每条都必须能判断通过或不通过。

## 1. 用户故事的格式

```
FUS3 — As a <角色>, I want <要做的事>, so that <业务上的好处>.
```

- **角色**必须是术语表里的角色名，不能写"用户"或"系统"。
- **要做的事**是一件完整的事，通常对应用例图里的一个用例。
- **好处**说业务价值，不说技术实现。"so that 数据存进数据库"不是好处；"so that 设备丢失时有据可查"才是。
- 一个故事只讲一件事。描述里出现"并且""以及"连接两个动作时，考虑拆成两个故事。
- 每个故事 3–6 条 AC。少于 3 条通常是没想清楚例外，多于 6 条通常是故事太大，需要拆分。

语言约定：故事和 AC 用用户的语言写；角色名、状态名等术语用术语表中的写法。如果用户需要英文版（例如提交作业或给外企团队），整份文档统一用英文。

## 2. 好的验收标准长什么样

| 特征 | 说明 | 反例 |
|---|---|---|
| 可观察 | 描述能看到、能检查的结果 | "系统正确处理申请" |
| 二元 | 只有通过和不通过两种结果 | "审批速度要快" |
| 单一 | 一条 AC 只检查一件事 | "能提交并能修改并会通知管理员" |
| 有依据 | 能追溯到某条 BR 或某个案例 | 凭空添加的要求 |
| 不写实现 | 说做到什么，不说怎么做 | "在 loans 表插入一行" |
| 量化 | 数字、期限、范围都写明 | "近期的记录" |

## 3. 两种写法

**规则式**：一句话描述一条规则。适合权限、校验、单一规则。

```
AC2: 协议未签署时，"登记借出"操作被拒绝，并提示"请先签署借用协议"。(BR-05)
```

**场景式（Given / When / Then）**：适合有前提条件、多个步骤或状态变化的情况，也最容易变成测试。

```
AC4: Given 一张状态为 OnLoan 的借用单，且应还日期已过
     When 系统执行到期检查
     Then 借用单状态变为 Overdue，且管理员收到逾期提醒。(BR-07, T4)
```

同一份文档里两种写法可以混用，但同一个故事内尽量统一。涉及状态转换的 AC 优先用场景式，并注明转换编号。

**优先用真实数据做例子。** 有现有材料时，Given 部分尽量直接引用材料中的（脱敏）记录，而不是编一个抽象的例子：

```
AC2: Given 台账记录 JY-0903 应还 9 月 10 日，When 9 月 15 日办理归还，
     Then 逾期 5 天，逾期费 50 元，与台账一致。(BR-10, T10)
```

这样做有三个好处：业务方一眼能认出是哪笔业务；AC 同时证明了规则与过去的实际做法一致（或者暴露出不一致）；这些例子可以直接成为演示脚本和测试数据。引用的数据必须与材料完全一致。

## 4. 每个故事该覆盖哪些方面

写完 AC 后，对照下表检查有没有漏掉的方面。不是每个故事都需要全部覆盖，但每一项都要想过。

| 方面 | 问自己 | 例子 |
|---|---|---|
| 主路径 | 一切正常时结果是什么？ | 提交后生成编号并进入 Requested 状态 |
| 校验 | 输入不对时怎么处理？ | 必填项缺失时不能提交，并指出缺哪一项 |
| 权限 | 谁能做、谁不能做？ | 只有管理员能审批；借用人看不到别人的申请 |
| 状态规则 | 在什么状态下才能做？ | 只有 Approved 状态才能登记借出 |
| 例外 | 例外清单中相关的项目处理了吗？ | 库存不足时进入等待名单 |
| 边界 | 数字和日期正好在边界上时怎样？ | 第 14 天当天归还不算逾期 |
| 留痕与通知 | 需要记录或通知谁吗？ | 审批结果通知申请人；操作写入审计日志 |

## 5. 改写示例

| 不好的写法 | 问题 | 改写后 |
|---|---|---|
| 系统应该方便用户提交申请。 | 不可观察，"方便"无法判断 | 申请表单只包含 BR-01 规定的 6 个必填项；提交成功后显示申请编号。 |
| 审批要及时。 | 不量化 | 申请提交 2 个工作日内未处理时，系统提醒审批人；3 个工作日仍未处理，提醒其上级。(BR-09) |
| 管理员可以管理借用单。 | "管理"太笼统 | 拆成：审批、驳回、登记借出、登记归还各一条 AC，或拆成多个故事 |
| 系统在 loans 表中把 status 更新为 Approved。 | 写了实现 | 审批通过后，借用单状态显示为"已批准"，申请人收到通知。 |
| 用户可以提交并修改申请，管理员会收到通知。 | 一条检查了三件事 | 拆成三条 AC |
| 逾期会被处理。 | 没说怎么处理、谁处理 | 归还时如已逾期，系统按 DT-03 计算罚款并显示给办事员确认。 |

## 6. 编号与追溯

- 故事编号：`FUS1`、`FUS2`……；`NFUS1`、`NFUS2`……
- AC 编号：`FUS3-AC2`，在故事内部从 1 开始。
- 每条 AC 末尾用括号注明依据：BR 编号、决策表编号、转换编号或案例编号，例如 `(BR-05, T3)`。
- 一条 BR 被多个 AC 引用是正常的；但一条 BR 一个 AC 都没有引用，说明它没有被验证，需求质量检查会把它找出来。
- 黄金案例与 AC 不同：AC 检查单条规则，黄金案例检查一整段真实过程。两者都要有。

## 7. 给用户确认时怎么呈现

非技术用户逐条读 AC 会很累。确认时：

1. 每个故事先用一句话说明它是干什么的。
2. AC 按"正常情况 → 不允许的情况 → 特殊情况"分组读。
3. 只把来自推断、需要确认的 AC 单独标出来请用户重点看，其余的让用户快速浏览。
