# 验证方法

阶段 5 和阶段 6 使用。"测试全部通过"本身证明不了什么：测试可能没测到点子上，静态检查可能查错了地方，演示脚本可能在现场卡住。本文件列出在完整示例中真正发现过问题的验证方法，以及每一步做到什么程度才算完成。

每种方法都配有完整示例中的实际文件（`examples/equipment-loan/app/`），照着改即可。

## 目录

1. 种子数据校验（5a）
2. 反向检查：证明测试会失败（5b 起每个阶段）
3. 角色走查：每一步都要断言（5c）
4. 端到端测试（阶段 6）
5. 演示脚本排练（阶段 6）
6. 各阶段完成标志

---

## 1. 种子数据校验（5a）

演示数据直接写入各种状态，不经过转换函数（`default-stack.md` 第 5 节），所以需要一组测试证明它们与规格一致。至少检查：

- 数量与分布：总量符合 NFUS 的数据量；每个状态至少有几条
- 日期：先后顺序合理（提交 → 审批 → 借出 → 归还）；状态与"今天"吻合（例如"借出中"的应还日期不能早于今天，否则应为"已逾期"）
- 资源不重叠：同一件物品不会同时借给两个人
- 决策表：每条记录的期限、审批人都符合 DT 表；审批顺序正确
- 计算：每笔费用按规则重算一遍，都一致
- 材料：从台账导入的记录逐条与原台账一致；不能导入的记录写进导入报告
- 黄金案例：起始数据都在，涉及的人和物品已预留
- 隐私：所有人员和联系方式都是虚构的

写完后，故意改坏一份数据库（颠倒审批顺序、制造重叠、改错金额），确认测试会失败。完整示例中，这组测试第一次运行就发现了 2 个种子数据错误。

示例：`tests/integration/seed-data.test.ts`（可通过 `SEED_DB` 环境变量指向一份故意改坏的数据库）。

## 2. 反向检查：证明测试会失败

做法：一次只埋一个典型错误，运行测试，测试必须失败；然后恢复代码，再埋下一个。用 `scripts/mutation_check.py` 自动完成，错误清单写在 `app/tests/mutations.json`。

每类规则至少埋一个：

| 类别 | 埋什么错误 |
|---|---|
| 决策表 | 边界改一个字符（`>` 改成 `>=`）；某一行的数值改掉 |
| 守卫 | 让守卫永远通过 |
| 权限 | 给某个角色多开一个不该有的操作；去掉"只能操作本人记录"的检查 |
| 状态转换 | 转换后不再触发下游动作（如等待名单不再释放） |
| 计算 | 去掉上限；日期边界差一天；工作日把周末算进去 |
| 通知 | 漏发一个人 |
| 静态检查 | 偷偷加一处删除数据、一处直接修改状态 |
| 界面 | 复选框的字段名写错；表单输入改回非受控 |

界面类错误要先构建再跑端到端测试：在清单里给这一条单独写 `cmd`，并给脚本加 `--after "npx next build"`，跑完后重新构建，不留下带错误的构建。

漏掉的错误说明测试有缺口：补上测试，再跑一次，直到全部发现。完整示例中第一轮 18 个漏了 2 个：一处双层权限只测了外层；一个统计边界没有测试，补测时又因为测试日期选错而没真正覆盖。

**静态检查本身也要反向检查。** 例如"代码中没有删除数据"这条检查：写得太宽，会把退出登录时删除 cookie 也当成删数据；改窄之后，又可能漏掉变量名不同的真删除。每写一条静态检查，就埋一次违规，确认它会报错。

## 3. 角色走查：每一步都要断言

用浏览器脚本以每个角色登录，走一遍主流程和例外流程。只截图不够：每次操作后，都要检查页面上出现了确认或错误信息，状态变成了预期的样子。完整示例中有两个问题是加了断言后才确认的：一个错误信息根本没有显示；批准后审批区域消失，管理员看不到任何确认。

每个角色至少包括：

- 登录后进入自己的首页，导航里只有自己能做的事
- 最常做的三件事从首页出发，3 次点击以内能开始（NFUS 易用性）
- **填错 → 只改错的那一项 → 再提交成功**。React 19 会在每次提交后重置表单，单元测试和集成测试都发现不了"已填的内容被清空"这类问题
- 越权：直接打开别人的记录、打开无权限的页面，被拒绝
- 借用人一类主要用手机的角色，用手机宽度（390 像素）走一遍
- 记录浏览器控制台的错误；预期中的错误（如 404）要单独说明
- 主要表单和工作页面做一次无障碍扫描（注入 axe-core，检查 WCAG 2 A/AA）

断言时注意时间：页面可能有一瞬间的中间状态（例如表单刚被重置、又被组件状态恢复）。读取结果时用"等到满足条件"的写法（Vitest 的 `expect.poll`、Playwright 的 `waitFor`），不要在操作后立刻读一次就下结论。

截图交给用户确认页面叫法、信息顺序和按钮位置。

## 4. 端到端测试（阶段 6）

- 每个黄金案例一个测试文件，按案例原文的步骤从界面操作，断言用户在页面上看到的结果（状态、金额、提示文字、通知内容、操作历史）。
- 每个测试文件用一份全新的演示数据和一个独立的服务，互不影响。
- 按页面上看得到的文字和标签找元素，不按内部字段名（`uml-to-code-mapping.md` 7.4）。
- 时间相关的案例，通过界面上的演示控制（"模拟今天"）推进日期，再点"运行到期检查"。
- 对端到端测试也做一次反向检查：至少埋一个领域错误和一个界面错误。

示例：`tests/e2e/harness.ts`、`tests/e2e/golden-cases/`、`tests/e2e/request-form.e2e.test.ts`。

## 5. 演示脚本排练（阶段 6）

演示脚本写好后，按脚本原文写一个自动排练测试，逐步执行脚本里的每个操作，检查观众应该看到的内容确实出现。完整示例中，第一次排练就发现脚本里随手选的一件设备正被一张逾期单占着，现场"批准"会失败。

- 脚本只用黄金案例和演示数据中预留的人和物品
- 脚本里写到的具体文字（金额、天数、提示语）都在排练中断言
- 修改演示数据或界面后，重新排练

示例：`tests/e2e/demo-script.e2e.test.ts`。

## 6. 各阶段完成标志

| 阶段 | 完成标志 |
|---|---|
| 5a 数据 | 种子数据校验测试全部通过，并用故意改坏的数据确认测试有效 |
| 5b 规则和权限 | AC、决策表、状态转换的测试全部通过；`mutation_check.py` 全部发现；`build_trace.py` 没有缺口 |
| 5c 界面 | 每个角色带断言的走查通过（含"填错 → 改正 → 再提交"）；控制台没有意外错误；无障碍扫描没有问题；正式构建通过 |
| 6 验证与交付 | 每个黄金案例的端到端测试通过；演示脚本排练通过；端到端测试的反向检查通过；`build_trace.py --test-report` 没有缺口 |
