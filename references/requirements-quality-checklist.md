# 需求质量清单

阶段 2 关卡使用。这份清单检查的是**需求本身写得好不好**，不是检查代码。可以把它理解为需求的"单元测试"：规格是用文字写的程序，这份清单就是它的测试。

## 怎么用

1. 用户故事全部写完后，逐项检查。
2. 每一项的结果是"通过"、"未通过"或"不适用"。未通过的写明具体位置和修改建议。
3. 所有项目通过、且规格中没有未解决的 `[待确认]`，才能通过阶段 2 的关卡。
4. 结果写入 `spec/02-quality-check.md`，格式见文末。

## 目录

1. 完整性
2. 清晰度
3. 一致性
4. 可测试性
5. 可追溯性
6. 范围
7. 模糊词清单
8. 结果格式

---

## 1. 完整性

| 编号 | 检查项 |
|---|---|
| Q01 | 角色视角表中每个角色"能做什么"的每一项，都有对应的用户故事 |
| Q02 | 每个核心流程从起点到终点的每一步，都被某个故事覆盖 |
| Q03 | 例外清单中回答"有"的每一项，都有故事或 AC 覆盖 |
| Q04 | 每张决策表都被至少一条 AC 引用 |
| Q05 | 每个黄金案例经过的每一步，都有对应的故事 |
| Q06 | CRUD 矩阵中每个"能创建""能修改"的格子，都有对应的故事 |
| Q07 | 项目约束中的每一条，都体现在某条 NFUS 或 BR 中 |
| Q08 | 要对接的每个现有系统，都有处理其不可用情况的 AC |
| Q09 | 有状态流转的实体，每种状态"如何进入、如何离开"都有故事说明 |

## 2. 清晰度

| 编号 | 检查项 |
|---|---|
| Q10 | 没有第 7 节模糊词清单中的词，或者出现的地方都已量化 |
| Q11 | 所有数字都有单位，期限写明是自然日还是工作日 |
| Q12 | 所有边界都写明了归属（"超过 5000"是否包含 5000） |
| Q13 | 每个故事的"好处"部分说的是业务价值，而不是技术实现 |
| Q14 | 没有一条 AC 同时检查多件事 |

## 3. 一致性

| 编号 | 检查项 |
|---|---|
| Q15 | 所有角色名、状态名、实体名都来自术语表，没有同义词混用 |
| Q16 | 同一条规则在不同故事中的说法一致（例如借期不能一处写 14 天、一处写两周但含义不同） |
| Q17 | 不同故事之间没有互相矛盾的要求（例如一处说"批准后不能修改"，另一处说"管理员可随时修改"） |
| Q18 | 故事中描述的权限与 CRUD 矩阵一致 |
| Q19 | NFUS 中的数字与 `00-brief.md` 中的业务量级相符 |

## 4. 可测试性

| 编号 | 检查项 |
|---|---|
| Q20 | 每条 AC 都能明确判断通过或不通过 |
| Q21 | 每条 AC 描述的是可以观察到的结果（界面显示、状态变化、收到通知、数据记录） |
| Q22 | 涉及状态变化的 AC 写明了前置状态和结果状态 |
| Q23 | 每条 NFUS 的 AC 都标注了验证方式（原型测试 / 原型演示 / 原型不验证） |

## 5. 可追溯性

| 编号 | 检查项 |
|---|---|
| Q24 | 每条 AC 都注明了依据（BR、决策表、转换或案例编号） |
| Q25 | 每条 BR 至少被一条 AC 引用 |
| Q26 | 每条 BR 都标明了出处（用户 / 材料 / 案例 / 模式库 / 推断） |
| Q27 | 出处为"模式库"或"推断"的内容，都已向用户确认，或仍标着 `[待确认]` |

## 6. 范围

| 编号 | 检查项 |
|---|---|
| Q28 | 没有超出阶段 0 确认范围的故事；如有，已经和用户确认要加入 |
| Q29 | 每个故事都能说清楚它解决了 `01-as-is.md` 中的哪个痛点，或支撑了哪个流程 |
| Q30 | 故事总数与规模档位相称（精简档不应出现几十个故事） |

## 7. 模糊词清单

出现以下词时，要么量化，要么删除：

| 模糊词 | 改成 |
|---|---|
| 及时、尽快、快速 | 具体时限："2 个工作日内""2 秒内" |
| 方便、友好、简单、直观 | 可检查的标准："不超过 3 次点击""必填项不超过 6 个" |
| 适当、合理、必要时 | 具体条件："金额超过 5000 时" |
| 一般、通常、大部分、基本上 | 明确的规则和例外分别写出 |
| 等、之类、相关 | 列出全部内容 |
| 支持、管理、处理 | 具体的动作："新建、修改、作废" |
| 安全、可靠、稳定 | 对应 NFUS 分类中的具体 AC |
| 尽量、争取 | 要么是要求，要么不是，不写"尽量" |
| 近期、长期、经常 | 具体时间范围或频率 |
| 灵活、可扩展 | 具体可配置的项（见 NFUS 可配置性） |

## 8. 结果格式

写入 `spec/02-quality-check.md`：

```markdown
# 需求质量检查

检查时间：YYYY-MM-DD
结果：通过 N 项，未通过 M 项，不适用 K 项
未解决的待确认项：X 个

## 未通过项

| 编号 | 位置 | 问题 | 修改建议 |
|---|---|---|---|
| Q10 | FUS5-AC3 | "审批要及时" | 改为"提交 2 个工作日内未处理时提醒审批人"，需确认天数 |
| Q25 | BR-11 | 没有任何 AC 引用 | 在 FUS7 中补一条 AC，或确认这条规则是否还需要 |

## 不适用项说明

| 编号 | 原因 |
|---|---|
| Q08 | 本项目不对接现有系统 |
```

修正后重新检查，直到全部通过。评审摘要中用业务语言说明检查发现并修正了什么。
