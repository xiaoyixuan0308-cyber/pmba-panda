# 决策表写法

阶段 1d 使用。业务规则中只要有**两个以上条件组合**决定结果，就写成决策表，不用文字描述。

## 为什么要用决策表

"外部供应商要财务审批，金额超过 5000 要总监审批" 这样的文字，读起来好像清楚，但两个条件都满足时怎么办？正好 5000 元算哪边？文字很容易漏掉组合，或在边界上含糊。决策表把每种组合列成一行，漏掉哪种组合一眼就能看出来。它还能直接变成代码中的查找表和逐行测试（见 `uml-to-code-mapping.md` 7.1）。

## 1. 什么时候用

- **用**：结果由两个以上条件共同决定。例如审批级别、费用计算、能否自动通过、走哪条流程。
- **不用**：只有一个条件（"逾期就罚款"），直接写成一条 BR 即可。
- 判断信号：用户的描述里出现"如果……而且……""要看情况""一般是……但如果……"。

## 2. 表的结构

```markdown
### DT-01 审批级别　(BR-02)

| 规则 | 金额 > 5000 | 外部供应商 | → 审批人 | 出处 |
|---|---|---|---|---|
| R1 | 否 | 否 | 主管 | [用户] |
| R2 | 否 | 是 | 主管、财务 | [用户] |
| R3 | 是 | 否 | 主管、总监 | [案例: GC-03] |
| R4 | 是 | 是 | 主管、财务、总监 | [推断] [待确认] |
```

- **编号**：`DT-xx`，并注明对应的 BR。
- **条件列**：每个条件一列，列名写成可以回答"是/否"或有限几个取值的问题。
- **结果列**：用 `→` 开头，与条件列区分。可以有多个结果列。
- **规则行**：`R1`、`R2`…… 每行是一种条件组合。
- **出处列**：每行单独标出处，因为用户往往只说了其中几行，其余是推断出来的。
- **唯一命中**：任何一组具体输入，必须**恰好命中一行**。不能没有命中，也不能同时命中两行。

## 3. 写表的六个步骤

**第 1 步：列出条件和取值。** 每个条件写清楚所有可能的取值。数字类条件要分段，并写明边界：

| 条件 | 取值 |
|---|---|
| 金额 | ≤ 5000 / > 5000 |
| 供应商类型 | 内部 / 外部 |

**第 2 步：确认边界。** 每个分段的边界都要问用户："正好 5000 元算哪一边？" 边界写成 `≤` 和 `>` 这样不会重叠的形式。

**第 3 步：算出组合数。** 各条件取值数相乘。2 个条件各 2 个取值，共 4 行；3 个条件各 2 个取值，共 8 行。超过 16 行时，考虑能否拆成两张表，或者有条件其实不影响结果。

**第 4 步：逐行填结果。** 用户说过的行标 `[用户]` 或 `[案例]`；没说过的行不要自己填一个看起来合理的结果，而是标 `[推断] [待确认]` 并向用户确认。

**第 5 步：合并无关条件。** 如果某个条件在若干行中不影响结果，可以用 `-`（任意）合并这几行：

| 规则 | 加急 | 金额 > 5000 | → 审批人 |
|---|---|---|---|
| R1 | 是 | - | 总监 |
| R2 | 否 | 否 | 主管 |
| R3 | 否 | 是 | 主管、总监 |

合并后要重新检查唯一命中：`-` 代表的每一种取值都要只命中一行。

**第 6 步：检查。**
- 完整：每种组合都被某一行覆盖
- 不重叠：没有任何组合同时命中两行
- 每行都有出处，`[待确认]` 的行已经问过用户
- 至少有一个黄金案例能在表中找到对应的行；如果所有黄金案例都只命中同一行，说明其他行缺少验证，需要再要一个案例

## 4. 给用户确认时怎么呈现

非技术用户读表格可能吃力。确认时把每一行翻译成一句话，逐行请用户确认：

> 我把审批规则整理成了 4 种情况，请逐条看对不对：
> 1. 金额不超过 5000、内部供应商：只要主管审批。
> 2. 金额不超过 5000、外部供应商：主管和财务都要审批。
> 3. 金额超过 5000、内部供应商：主管和总监都要审批。
> 4. 金额超过 5000、外部供应商：主管、财务和总监都要审批。（这一条是我推出来的，请特别确认。）

规格中保留表格形式，翻译成的句子放进评审摘要。

## 5. 常见错误

| 错误 | 后果 | 预防 |
|---|---|---|
| 边界重叠（`≥5000` 和 `≤5000` 同时出现） | 正好 5000 时命中两行 | 统一用 `≤` / `>` |
| 漏掉组合 | 程序遇到这种情况时不知道怎么处理 | 先算组合数，再逐行填 |
| 自己填了没说过的行且没标注 | 推断被当成事实写进代码 | 没说过的行一律标 `[推断] [待确认]` |
| 条件写成模糊的词（"金额较大"） | 无法实现，也无法测试 | 每个条件都量化 |
| 结果里混入流程步骤（"先通知再审批"） | 表和活动图职责混乱 | 表只给出结果，顺序交给活动图 |
| 表改了，图和代码没改 | 规则不一致 | 改表走变更流程，按追溯矩阵更新下游 |

## 6. 完整例子

虚构的设备借用系统，借用期限规则（BR-06）。

用户原话：`[用户]` "一般借两周；笔记本这类贵重的只能借一周；如果是老师借教学用，可以借一个月，贵重的也最多两周。"

```markdown
### DT-02 借用期限　(BR-06)

| 规则 | 借用人类型 | 用途 | 贵重设备 | → 最长期限 | 出处 |
|---|---|---|---|---|---|
| R1 | 学生 | - | 否 | 14 天 | [用户] |
| R2 | 学生 | - | 是 | 7 天 | [用户] |
| R3 | 教师 | 教学 | 否 | 30 天 | [用户] |
| R4 | 教师 | 教学 | 是 | 14 天 | [用户] |
| R5 | 教师 | 非教学 | 否 | 14 天 | [推断] [待确认] |
| R6 | 教师 | 非教学 | 是 | 7 天 | [推断] [待确认] |
```

检查：借用人 2 种 × 用途 2 种 × 贵重 2 种 = 8 种组合。R1、R2 中的 `-` 各覆盖 2 种，共 4 种；R3–R6 共 4 种；合计 8 种，完整且不重叠。R5、R6 用户没有说过，需要确认"老师借去非教学用途，是不是按一般规则"。

对应的测试（见 `uml-to-code-mapping.md` 7.1）：每行一个，共 6 个，外加边界测试"借用第 14 天当天是否算逾期"。
