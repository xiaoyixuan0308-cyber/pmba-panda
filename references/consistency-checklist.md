# 一致性检查清单

阶段 3 画完所有图之后、进入阶段 4 之前执行。目标是确保规格文件和五种模型说的是**同一件事**，因为任何不一致都会被映射成代码里的缺陷（见 `uml-to-code-mapping.md`）。

## 怎么用

1. 先运行 `python3 scripts/check_consistency.py <项目目录>`，它完成标有"自动"的检查（A1 的语法检查需要本地有 PlantUML，可先运行 `scripts/render_uml.sh`），并生成报告初稿。
2. 再由 Claude 逐条人工检查标有"人工"的项目。
3. 把结果写入 `spec/models/consistency-report.md`，格式见文末。
4. 有任何"阻断"级问题时，不能通过阶段 3 的关卡：先修模型或规格，再重新检查。"警告"级问题告诉用户，由用户决定是否修改。

修改时遵循一个原则：**术语表和业务规则是基准**。图和规格冲突时，先确认业务规则怎么说，再改图；业务规则本身有问题，就走变更流程。

## A. 单张图的结构检查

每张图单独检查一遍，详细写法见 `plantuml-pitfalls.md`。

| 编号 | 检查项 | 方式 | 级别 |
|---|---|---|---|
| A1 | 所有图都能渲染，没有 Syntax Error | 自动 | 阻断 |
| A2 | 用例图：include 从基础用例指向被包含用例；extend 从扩展用例指向基础用例，且写明条件 | 人工 | 阻断 |
| A3 | 用例图：参与者都在系统边界外；外部系统带 `<<system>>` 标记；父角色至少连接一个用例 | 人工 | 警告 |
| A4 | 活动图：只有一个起点；每条路径都能走到结束节点，没有走不通的死路 | 人工 | 阻断 |
| A5 | 活动图：每个决策点的出边条件互斥且完整（有 `[else]` 或覆盖所有情况） | 人工 | 阻断 |
| A6 | 活动图：每个 fork 都有对应的 join；没有分支在 join 之前结束流程 | 人工 | 阻断 |
| A7 | 活动图：每个动作都在正确的泳道里（渲染后逐个核对） | 人工 | 阻断 |
| A8 | 状态机图：每个状态都能从初始状态到达 | 自动 | 阻断 |
| A9 | 状态机图：除终止状态外，每个状态都有出去的转换 | 自动 | 阻断 |
| A10 | 状态机图：每条转换都有触发和编号（`T1`……）；同一状态、同一触发的多条出边，守卫互斥 | 自动 + 人工 | 阻断 |
| A11 | 序列图：所有 `alt` / `opt` / `loop` 都有 `end`；同步调用用实线、返回用虚线 | 自动 | 警告 |
| A12 | 类图：每条关联两端都有多重性；组合、聚合菱形在整体一端；泛化三角形在父类一端 | 人工 | 阻断 |
| A13 | 状态机图：转换效果不与目标状态的 entry 动作重复（例如转换上写了"通知借用人"，目标状态的 entry 也"通知借用人"，照图实现会通知两次）。重复时保留 entry，删掉转换上的效果 | 自动 | 阻断 |

## B. 命名一致性

| 编号 | 检查项 | 方式 | 级别 |
|---|---|---|---|
| B1 | 所有图中出现的类名、状态名、角色名、实体名都在术语表中 | 自动 | 阻断 |
| B2 | 同一个概念在不同图里只用一个名字（例如不能一处叫 `Borrower`，另一处叫 `Applicant`） | 自动 | 阻断 |
| B3 | 术语表里的每个实体、状态、角色至少在一张图中出现；没出现的要么删掉，要么说明原因 | 自动 | 警告 |
| B4 | 大小写和拼写完全一致（`OnLoan` 与 `Onloan` 视为不一致） | 自动 | 阻断 |

## C. 用例图 ↔ 规格

| 编号 | 检查项 | 方式 | 级别 |
|---|---|---|---|
| C1 | 用例图的参与者 = 参与者清单 = 角色视角表中的角色（外部系统除外） | 自动 | 阻断 |
| C2 | 角色视角表中每个角色"能做什么"的每一项，都有对应的用例与该角色相连 | 人工 | 阻断 |
| C3 | 用例图的连线、CRUD 矩阵、用户故事的 AC 三方一致：某角色连着"Approve Loan"，CRUD 矩阵里该角色就必须能修改 Loan；AC 写"办事员和设备管理员都可以办理归还"，CRUD 矩阵里两个角色就都要有归还时需要的全部权限（包括登记逾期费已缴这类附带操作） | 人工 | 阻断 |
| C4 | 每个功能用户故事（FUS）至少对应一个用例 | 人工 | 阻断 |
| C5 | 每个 extend 的条件对应一条 BR | 人工 | 警告 |
| C6 | 阶段 0 记录的要对接的现有系统，都以外部参与者出现 | 人工 | 警告 |

## D. 活动图 ↔ 状态机图

这是最容易出错、后果也最严重的一组：活动图说"做了什么"，状态机说"之后变成什么状态"，两者必须对得上。

| 编号 | 检查项 | 方式 | 级别 |
|---|---|---|---|
| D1 | 活动图中每个会改变核心实体状态的动作，在状态机中都有对应的转换（例如"Reject loan"对应到 `Rejected` 的转换） | 人工 | 阻断 |
| D2 | 状态机中每条由用户触发的转换，在某张活动图中都有对应的动作 | 人工 | 阻断 |
| D3 | 活动图决策点的条件与状态机对应转换的守卫，使用同一个术语表名称，并引用同一条 BR | 人工 | 阻断 |
| D4 | 活动图中的回流（如"重新评估"）在状态机中有对应的回到先前状态的转换 | 人工 | 阻断 |
| D5 | 活动图的结束节点对应状态机中的终止状态或稳定状态 | 人工 | 警告 |
| D6 | 活动图中的泳道角色，与状态机转换上绑定的执行角色一致 | 人工 | 阻断 |

## E. 活动图 ↔ 序列图

| 编号 | 检查项 | 方式 | 级别 |
|---|---|---|---|
| E1 | 每张序列图都对应一张活动图（或活动图中的一段），在说明卡里写明对应关系 | 人工 | 阻断 |
| E2 | 序列图中 `alt` 的每个分支，对应活动图中一个决策点的一个出边，条件说法一致 | 人工 | 阻断 |
| E3 | 活动图的并行分支（fork），在序列图中体现为 `par` 或依次执行的独立调用，并注明它们互不依赖 | 人工 | 警告 |
| E4 | 消息的先后顺序与活动图中动作的先后顺序一致 | 人工 | 阻断 |
| E5 | 活动图的泳道角色，与序列图中发起操作的参与者一致 | 人工 | 警告 |

## F. 序列图 ↔ 类图

| 编号 | 检查项 | 方式 | 级别 |
|---|---|---|---|
| F1 | 序列图中领域对象生命线的名称都是类图中的类名 | 自动 | 阻断 |
| F2 | 发给领域对象生命线的每条消息，在类图中该类（或其父类）的操作里都能找到 | 自动 | 阻断 |
| F3 | 消息参数和返回值使用的类型，在类图中有定义 | 人工 | 警告 |
| F4 | 序列图中的外部系统生命线，在用例图中有对应的外部参与者 | 自动 | 警告 |

## G. 状态机图 ↔ 类图

| 编号 | 检查项 | 方式 | 级别 |
|---|---|---|---|
| G1 | 状态机描述的实体在类图中有对应的类，且该类有 `status` 属性 | 自动 | 阻断 |
| G2 | `status` 属性的类型是枚举，枚举值与状态机中的状态完全一致（不多不少） | 自动 | 阻断 |
| G3 | 状态机中 entry / exit / do 和转换效果里调用的动作，能在类图中对应类的操作里找到，或在说明卡里注明由服务层实现 | 人工 | 警告 |
| G4 | 守卫中引用的数据（如 `agreementSigned`）和转换效果需要保存的数据（如"记录取消原因"需要一个存原因的属性、"通知"需要一个通知类或注明由外部系统负责），在类图中都有地方存；构建计划中提到的每一种存储也都能在类图中找到 | 人工 | 阻断 |

## H. 规格 ↔ 模型的覆盖

| 编号 | 检查项 | 方式 | 级别 |
|---|---|---|---|
| H1 | 每条 BR 至少体现在一个模型元素上（守卫、决策点、多重性、extend 条件等） | 人工 | 阻断 |
| H2 | 每张决策表在活动图或状态机中有引用它的决策点或守卫 | 人工 | 阻断 |
| H3 | 每个黄金案例都能在活动图上从头到尾走一遍，并在状态机上得到期望的最终状态 | 人工 | 阻断 |
| H4 | 例外清单中确认"有"的每一项例外，在活动图中都有对应的路径 | 人工 | 阻断 |
| H5 | CRUD 矩阵中每个"能创建"的格子，在某张图中有对应的创建动作 | 人工 | 警告 |
| H6 | 模型中没有规格里找不到依据的元素（凭空多出来的功能、状态或规则） | 人工 | 警告 |
| H7 | 黄金案例中引用的人、记录、编号、日期和金额与现有材料一致；不一致的已列入矛盾清单由用户裁决，没有改写任何一方 | 人工 | 阻断 |
| H8 | 状态机中每条转换效果、每个 entry / do / exit 动作，在 .puml 中紧挨着的上一行注释里写明依据（`' BR-07`、`' FUS8 AC1`、`' [用户]`）。写不出依据的，说明没人说过何时做、对谁做，回到规格向用户确认 | 自动 | 警告 |
| H9 | 反过来核对：每条 BR 和 AC 中"通知谁""释放什么""记录什么"，都在对应转换的效果或目标状态的动作中出现（例如"归还后通知等待的人"要求归还转换有"释放设备"效果） | 人工 | 阻断 |

## I. 结果报告格式

写入 `spec/models/consistency-report.md`：

```markdown
# 一致性检查报告

检查时间：YYYY-MM-DD
自动检查：通过 N 项，未通过 M 项
人工检查：通过 N 项，未通过 M 项

## 未通过项

| 编号 | 级别 | 位置 | 问题 | 建议修改 |
|---|---|---|---|---|
| D1 | 阻断 | 02-activity-loan / "Reject loan" | 状态机中没有到 Rejected 的转换 | 在 03-state-loan 中加 Requested → Rejected 的转换 T2 |
| B2 | 阻断 | 04-sequence-checkout | 生命线叫 Applicant，术语表为 Borrower | 统一改为 Borrower |

## 用户需要决定的警告

| 编号 | 位置 | 问题 | 选项 |
|---|---|---|---|
```

报告的结论部分同时写进本阶段的评审摘要（用业务语言，例如"流程图和状态图有一处对不上：拒绝申请后，系统里的状态没有变化。已修正。"）。
