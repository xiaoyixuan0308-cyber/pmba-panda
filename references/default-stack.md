## 1. 为什么选这套

- **一条命令就能在本地跑起来。** 不需要单独安装和配置数据库服务器，数据存在项目里的一个文件中，适合非技术用户自己运行和演示。
- **权限和规则天然在服务端执行。** 页面操作通过服务端函数完成，守卫和权限检查放在服务端，符合 `uml-to-code-mapping.md` 的要求。
- **数据结构有类型检查。** 类图转成的数据表结构带类型，字段写错在构建时就会报错。
- **已在完整示例中跑通过。** `examples/equipment-loan/app/` 用这套组合实现了角色权限、状态流转、审计日志、演示数据和全部测试，可以直接参照。

## 2. 技术组成

| 用途 | 选择 | 说明 |
|---|---|---|
| 运行环境 | Node.js 20.9 或更新版本 | 用户机器上唯一需要提前安装的东西 |
| 应用框架 | Next.js（App Router）+ TypeScript | 页面和服务端函数在同一个项目里 |
| 数据库 | SQLite（better-sqlite3） | 单文件数据库，无需服务器 |
| 数据访问 | Drizzle ORM | 类图 → 表结构；迁移由 drizzle-kit 生成 |
| 输入校验 | zod | 服务端校验必填项、格式和范围 |
| 登录与会话 | bcryptjs（密码哈希）+ jose（签名会话） | 会话密钥从环境变量读取 |
| 界面组件 | Tailwind CSS + shadcn/ui + lucide 图标 | 组件可直接修改，不锁定在某个组件库里；组件库连不上时见第 8 节 |
| 字体 | 只用系统字体（列出中文字体） | 不从网上下载字体，演示现场断网也能正常显示 |
| 提示消息 | 页面内的提示框（可选 sonner） | 操作成功、失败的提示 |
| 脚本运行 | tsx | 运行初始化和演示数据脚本 |
| 单元与集成测试 | Vitest | 规则、决策表、状态转换、权限的测试 |
| 端到端测试 | Playwright | 黄金案例、角色走查、演示脚本排练；使用环境中已经安装的版本（第 8 节） |
| 无障碍检查 | axe-core | 把 `axe.min.js` 注入页面后运行，与测试工具版本无关 |

版本：使用安装时的稳定版本，由 `package-lock.json` 锁定。不要在规格中写死版本号。

## 3. 项目结构

目录与 `uml-to-code-mapping.md` 中的映射一一对应：

```
app/
  src/
    db/
      schema.ts               类图 → 表结构（2.x）
      client.ts               数据库连接
    domain/
      <entity>/
        transitions.ts        状态机 → 转换表（3.2）
        transition.ts         唯一的状态变更函数（3.2）
        guards.ts             守卫函数，每个带 BR 编号（3.2）
        service.ts            类图操作 / 序列图消息 → 服务函数（2.3、5.2）
    rules/
      decision-tables.ts      决策表 → 数据 + 查找函数（7.1）
    auth/
      permissions.ts          CRUD 矩阵 → 权限配置（7.2）
      session.ts              登录会话
    audit/
      log.ts                  统一审计日志（7.5）
    adapters/
      <external-system>/
        index.ts              外部系统接口（5.4）
        mock.ts               模拟实现
    app/
      (public)/               登录前页面
      (app)/                  登录后页面，按角色显示导航（7.3）
        <role-home>/          每个角色的首页
        <entity>/             各实体的列表和详情
  scripts/
    setup.ts                  建表 + 写入演示数据
    demo-data.ts              演示数据（全部虚构，覆盖正常和例外路径）
  tests/
    unit/                     决策表、守卫、校验
    integration/              状态转换、权限、序列图主路径
    e2e/
      harness.ts              每个测试文件用一份全新数据库和一个独立服务
      golden-cases/           每个黄金案例一个测试
      role-walkthrough/       每个角色走一遍主流程（带断言）
      demo-script.e2e.test.ts 按演示脚本原文排练
    mutations.json            反向检查要埋入的错误（verification-playbook.md）
  data/                       SQLite 数据库文件（不提交到版本库）
  public/uploads/             上传的文件（不提交到版本库）
  .env.example                环境变量示例
  README.md
```

## 4. 常用命令

在 `package.json` 中提供以下脚本，README 只写这几条：

| 命令 | 作用 |
|---|---|
| `npm install` | 第一次运行前安装依赖 |
| `npm run setup` | 建库并写入演示数据；随时重跑可以把数据恢复到初始状态 |
| `npm run dev` | 启动原型，在浏览器打开 `http://localhost:3000` |
| `npm test` | 运行单元和集成测试 |
| `npm run test:e2e` | 先构建，再运行黄金案例、角色走查和演示脚本排练 |

## 5. 构建约定

- **命名**：表名、字段名、状态值、角色名一律取自术语表的英文名（`uml-to-code-mapping.md` 第 8 节）。
- **状态只能通过转换函数修改**：在代码审查和测试中都要检查，不允许任何地方直接写 `status`。
- **服务端校验优先**：所有输入用 zod 在服务端校验；界面上的校验只是提前提示。
- **权限双重体现**：服务端按 `permissions.ts` 拒绝越权操作；界面按同一份配置隐藏不可用的按钮。
- **金额用整数存储**：以分为单位，显示时再换算。
- **日期和时间分开存**：只有日期、没有具体时间的字段（借用日期、应还日期、生日）存 `YYYY-MM-DD` 文本，按日历日比较和相加，不受时区影响；有具体时刻的字段（提交时间、审批时间）存 UTC 时间戳，显示时按用户所在时区转换。把日期存成时间戳，常见后果是跨时区时"应还日期"错一天。
- **种子数据可以直接写入状态，但要有校验测试**：演示数据需要各种状态的历史记录，可以直接插入，不必一步步走转换函数；但必须有一组数据校验测试证明它们与规格一致（日期先后、审批顺序、决策表、费用、设备不重叠、与材料逐条吻合），并用故意埋错的数据确认这些测试有效（`verification-playbook.md` 第 1 节）。运行时的所有状态变化仍然只能通过转换函数。
- **会返回校验错误的表单用受控输入**：React 19 的表单动作在每次提交后会重置表单。服务端返回"某项填错"时，用户已经填好的其他内容会被清空，只能重填。所以这类表单的每个输入项都放进组件状态（受控组件），角色走查中必须有"填错 → 只改错的那一项 → 再提交成功"这一步。
- **每个操作都有看得见的结果**：成功显示确认，失败显示原因，提示放在用户眼前。操作完成后按钮所在的区域如果消失（例如批准后审批区不再显示），要在页面上保留一条"你已于某时批准"之类的记录。
- **框架选项从简**：Next.js 16 的模板默认开启 `cacheComponents`，实时读数据库的页面必须额外处理，否则报错。原型关闭这个选项，在需要实时数据的页面和布局开头调用 `await connection()`。
- **规则可追溯**：实现 BR 的位置加 `// BR-xx` 注释；测试名带上故事、AC、决策表或黄金案例编号。
- **会话密钥**：开发环境可以使用临时密钥；生产环境未设置足够长度的密钥时，程序拒绝启动。
- **不接真实外部服务**：邮件、短信、企业微信、第三方系统一律走 `adapters/` 下的模拟实现。

## 6. 演示相关的约定

- **演示账号**：每个角色至少一个账号；同一角色下有子类型、而子类型影响规则的（如借用人分学生和教师，借期上限不同），每个子类型各一个账号。账号名直接体现角色（例如 `manager@demo.local`），密码统一写在 README 中，并注明仅用于演示。
- **演示数据**：全部虚构；覆盖每个状态至少一条记录，每个黄金案例的起始数据都准备好，每种已确认的例外至少一条可演示的数据。黄金案例和演示脚本用到的人和物品要预留，生成历史数据时避开它们，否则演示时可能撞上一条正在占用的记录。
- **模拟标注**：凡是用到模拟外部系统结果的页面，显示"模拟数据"标记。
- **时间相关规则的演示**：管理员页面提供"运行到期检查"按钮，用来演示逾期、超时、有效期等时间触发；README 说明正式系统应改为定时任务。
- **重置**：演示前运行 `npm run setup`，数据恢复到初始状态。

## 7. 用户要换技术栈时

`uml-to-code-mapping.md` 中的映射关系与技术栈无关，换栈时保持不变，只换写法。需要在阶段 4 的构建计划中写明替代方案：

| 本文件中的部分 | 换栈时需要说明的替代 |
|---|---|
| SQLite + Drizzle | 用什么数据库、如何从类图生成表结构 |
| 服务端函数 | 服务端在哪里执行守卫和权限检查 |
| Vitest / Playwright | 单元测试和端到端测试分别用什么 |
| 一条命令运行 | 非技术用户如何启动原型 |

常见的情况：

- **用户公司指定了技术栈**（例如 Java + Spring）：按公司技术栈写，项目结构按第 3 节的分层对应过去。
- **用户要做成低代码平台上的应用**：本 skill 的阶段 0–4 照常使用，产出的规格和模型作为在低代码平台上配置的依据；阶段 5 改为输出配置清单，不生成代码。
- **用户只要规格和模型，不要原型**：在阶段 4 结束，交付规格、模型、追溯矩阵和评审摘要。

## 8. 网络受限或离线时

工作区和演示现场的网络常常受限（只允许软件包仓库，或会议室没有外网）。原则：原型运行时不依赖任何外部网络。

- **字体和图标**：只用系统字体；图标用 npm 安装的 lucide，不用在线图标或 CDN。
- **组件库**：shadcn/ui 的命令行工具要访问它的组件注册网站。访问不了时，不要反复重试，按同样的风格手写原型需要的少量组件（按钮、卡片、状态标签、提示框、带说明的输入项），放在 `src/components/ui.tsx`。原型通常只需要这几种。
- **浏览器测试工具**：环境里可能已经预装了 Playwright 和对应的浏览器。先查已安装的版本（`npm ls -g playwright` 或 `node -e "console.log(require('playwright/package.json').version)"`），项目里固定使用同一个版本（`npm i -D playwright@<该版本>`）。装了不同的版本，会找不到浏览器，而下载浏览器又需要外网。Python 版 Playwright 也可以用来截图和走查。
- **无障碍扫描**：直接把 `node_modules/axe-core/axe.min.js` 注入页面运行，不另装与 Playwright 绑定的扫描包。
- **交给用户时**：README 写明第一次运行端到端测试前执行 `npx playwright install chromium`（用户自己的电脑通常能上网）。
